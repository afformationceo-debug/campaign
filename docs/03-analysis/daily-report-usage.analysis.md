# Daily Report Usage Guide

> Feature: `daily-report`
> Purpose: 담당자별 업무 화면과 일일 보고서 화면을 실제 운영에서 어떻게 나눠 쓰는지 정의
> Updated: 2026-03-03

---

## 1. 기능 역할 분리

### 담당자별 업무

- 목적: 오늘 해야 할 일을 실제로 수행하고 상태를 남기는 실행 화면
- 사용자 행동: 상태 변경, Step 체크, 결과값 기록
- 보는 사람: 실무 담당자 본인, 운영 리더, 팀장
- 질문: `오늘 무엇을 진행 중인가?`, `어디까지 했는가?`

### 일일 보고서

- 목적: 하루 동안 실제로 나온 결과와 변화, 이슈, 지원 요청을 정리하는 리뷰 화면
- 사용자 행동: 자동 수집된 근거를 보고 결과/영향/리스크/지원 요청/내일 집중 작성
- 보는 사람: 팀장, 관리자, 협업 리더
- 질문: `그래서 오늘 무엇이 바뀌었는가?`, `무엇을 도와줘야 하는가?`

### 운영 원칙

- 담당자별 업무에는 `사실`을 남긴다.
- 일일 보고서에는 `의미`를 남긴다.
- 같은 내용을 두 번 길게 쓰지 않는다.
- 결과 근거는 낮에 쌓고, 해석은 마감 전에 한 번 한다.

## 2. 직원 교육용 사용 가이드 문구

### 2-1. 한 줄 안내

`담당자별 업무`는 일을 하는 화면이고, `일일 보고서`는 오늘 나온 결과를 설명하는 화면입니다.

### 2-2. 직원 행동 플로우

#### 오전: 오늘 할 일 확인

1. `담당자별 업무`에 들어가 오늘 배정된 업무를 확인합니다.
2. 바로 착수한 업무는 상태를 `진행중`으로 바꿉니다.
3. Step가 있는 업무는 실제 진행 순서대로 체크합니다.

#### 낮: 결과 근거 누적

1. 업무가 진행되면 `결과값`에 링크, 숫자, 산출물, 짧은 메모를 남깁니다.
2. 완료되면 상태를 `완료`로 바꾸고 결과값을 비워두지 않습니다.
3. 막힌 상태라면 `진행중`으로 유지하고 결과값이나 메모에 대기 사유를 남깁니다.

#### 퇴근 전: 하루 결과 정리

1. `일일 보고서` 화면으로 이동합니다.
2. 시스템이 모아준 자동 근거를 먼저 확인합니다.
3. 아래 5개만 짧고 분명하게 작성합니다.

- 오늘 나온 결과
- 영향 / 변화
- 막힌 이슈 / 리스크
- 지원 필요 / 의사결정 요청
- 내일 집중

### 2-3. 결과값 작성 기준

결과값은 `업무를 했다`가 아니라 `무엇이 남았는지`가 보여야 합니다.

#### 나쁜 예시

- 확인 완료
- 고객 응대함
- 광고 작업함
- 수정 중

#### 좋은 예시

- 광고 세팅 QA 완료, 고객 공유 링크 전달
- 고객 피드백 3건 반영 후 최종안 검토 요청
- 정산표 업데이트 후 운영 채널 공지
- 인플루언서 12명 발송 완료, 회신 4명 확보

### 2-4. 일일 보고서 작성 느낌

일일 보고서는 체크리스트를 다시 적는 곳이 아닙니다.

#### 직원에게 보여줄 문구 예시

`시스템이 오늘의 업무 근거는 자동으로 모아줍니다.`
`직접 적을 내용은 결과의 의미, 영향, 리스크, 도움 요청만 남겨주세요.`

#### 좋은 작성 예시

- 오늘 나온 결과:
  Alpha 캠페인 광고 세팅 QA를 마무리했고 고객에게 최종 링크를 전달했습니다.
- 영향 / 변화:
  내일부터 운영 집행이 가능한 상태가 되었고 일정 지연 리스크가 해소되었습니다.
- 막힌 이슈 / 리스크:
  Beta 캠페인은 고객 최종 피드백 회신이 늦어져 확정이 하루 밀릴 가능성이 있습니다.
- 지원 필요 / 의사결정 요청:
  내일 오전까지 회신이 없으면 AM 리마인드 지원이 필요합니다.
- 내일 집중:
  Beta 피드백 반영과 발송 대상 최종 확정에 집중하겠습니다.

### 2-5. 직원 교육 시 강조할 운영 룰

- `완료` 처리한 업무는 결과값이 비어 있지 않아야 한다.
- `진행중`인 업무는 무엇이 막혀 있는지 보여야 한다.
- 일일 보고서에는 체크 화면에 이미 있는 내용을 길게 복사하지 않는다.
- `지원 필요`는 모호하게 쓰지 않고 누가 어떤 결정을 해주면 되는지 적는다.

## 3. 팀장용 검토 기준

### 3-1. 팀장이 담당자별 업무에서 볼 것

- 오늘 누가 어떤 업무를 실제로 진행했는가
- `진행중`인데 오래 머무는 업무가 무엇인가
- 결과값 없이 `완료`만 찍힌 업무가 있는가
- Step가 있는 업무에서 중간에 멈춘 구간이 있는가

### 3-2. 팀장이 일일 보고서에서 볼 것

- 오늘 실제로 완료된 결과가 무엇인가
- 그 결과가 일정, 고객, 매출, 품질에 어떤 영향을 줬는가
- 내일 문제가 될 수 있는 리스크가 무엇인가
- 내가 지금 निर्णय하거나 지원해야 할 항목이 있는가

### 3-3. 검토 질문 체크리스트

#### 결과 확인

- 오늘 나온 결과가 문장으로 분명히 보이는가
- `한 일`이 아니라 `바뀐 상태`가 적혀 있는가
- 자동 근거와 서술 보고가 서로 맞는가

#### 리스크 확인

- `진행중` 항목 중 내일 병목이 될 일이 있는가
- 고객 대기, 승인 대기, 타부서 대기 항목이 있는가
- 결과값이 빈 `완료` 업무가 반복되는 담당자가 있는가

#### 지원 판단

- 지원 필요 항목이 구체적인가
- 팀장이 결정해야 할 것과 담당자가 계속 처리할 수 있는 것이 구분되는가
- 오늘 바로 개입해야 하는 항목이 무엇인가

### 3-4. 확인완료 처리 기준

팀장은 아래 조건이 충족될 때 `확인완료`로 본다.

- 오늘 나온 결과가 한 줄 이상 명확하다.
- 자동 근거와 보고 내용이 크게 어긋나지 않는다.
- 리스크가 있으면 리스크와 대응 요청이 적혀 있다.
- 내일 집중 항목이 비어 있지 않거나, 완료로 하루가 종료된 이유가 보인다.

### 3-5. 팀장 피드백 문구 예시

#### 좋은 피드백

- 결과는 명확한데 영향 설명이 부족하니 고객 일정 기준으로 한 줄만 더 적어주세요.
- 진행중 항목은 좋은데 무엇이 대기 사유인지 결과값에 남겨주세요.
- 지원 요청이 올라와 있어 내일 오전에 고객 리마인드 진행하겠습니다.

#### 피해야 할 피드백

- 더 자세히 써주세요.
- 그냥 꼼꼼히 적어주세요.
- 느낌이 잘 안 옵니다.

모호한 피드백은 보고 품질을 올리지 못합니다. 항상 `무엇이 비어 있는지`를 특정해서 말해야 합니다.

## 4. 실제 예시 데이터를 넣은 화면 시나리오

### 4-1. 상황

- 담당자: Alice
- 날짜: 2026-03-03
- 캠페인:
  - Alpha Launch
  - Beta Retention

### 4-2. 담당자별 업무에서의 실제 입력

#### 오전 9:10

- 전역 업무 `정산 공유`
  - 상태: `진행중`
  - 결과값: `2월 정산표 정리 중`

#### 오전 10:05

- 전역 업무 `정산 공유`
  - 상태: `완료`
  - 결과값: `정산표 공유 및 팀 채널 공지`

#### 오전 11:20

- Alpha Launch / `광고 세팅 QA`
  - Step 1: `세팅 확인` 완료
  - Step 2: `보고` 대기
  - 상태: `완료`
  - 결과값: `광고 세팅 QA 완료, 고객 공유 링크 전달`

#### 오후 3:40

- Beta Retention / `고객 피드백 반영`
  - 상태: `진행중`
  - 결과값: `고객 검토 회신 대기`

#### 오후 5:50

- 전역 업무 `CRM 세그먼트 점검`
  - 상태: 미체크 또는 `미완료`
  - 결과값: 없음

### 4-3. 시스템이 일일 보고서에서 자동으로 보여주는 것

#### 자동 수집된 오늘 결과

- 정산 공유 / 전역 업무 / 완료 / `정산표 공유 및 팀 채널 공지`
- 광고 세팅 QA / Alpha Launch / 완료 / `광고 세팅 QA 완료, 고객 공유 링크 전달`
- 고객 피드백 반영 / Beta Retention / 진행중 / `고객 검토 회신 대기`

#### 후속 확인 / 리스크

- 고객 피드백 반영 / Beta Retention / 진행중
- CRM 세그먼트 점검 / 전역 업무 / 미완료

#### 근거 상세

- 완료 2건
- 결과 근거 3건
- 후속 확인 2건
- Step 진행 1/3

### 4-4. 직원이 일일 보고서에 실제로 기입하는 문장

#### 오늘 나온 결과

Alpha Launch 광고 세팅 QA를 마무리하고 고객에게 최종 링크를 전달했습니다. 전역 정산표도 공유 완료했습니다.

#### 영향 / 변화

Alpha Launch는 내일부터 운영 집행 가능한 상태가 되었고, 정산 공유까지 끝나서 내부 커뮤니케이션 지연 요소가 줄었습니다.

#### 막힌 이슈 / 리스크

Beta Retention은 고객 최종 회신 대기 중이라 수정 반영이 내일 오전으로 밀릴 수 있습니다. CRM 세그먼트 점검은 오늘 처리하지 못했습니다.

#### 지원 필요 / 의사결정 요청

내일 오전 10시까지 Beta 고객 회신이 없으면 AM 차원의 리마인드 지원이 필요합니다.

#### 내일 집중

Beta Retention 피드백 반영과 CRM 세그먼트 점검 마무리에 집중하겠습니다.

### 4-5. 이 시나리오에서 팀장이 보는 포인트

- Alpha는 오늘 실제로 전진했다.
- Beta는 내일 병목 가능성이 있다.
- CRM 점검은 우선순위 재조정이 필요하다.
- 지원 요청은 `고객 리마인드`로 구체적이다.

즉, 팀장은 `누가 몇 개 체크했나`보다 `오늘 무엇이 끝났고, 내일 어디가 막히는가`를 바로 읽을 수 있어야 한다.

## 5. 도입 메시지 초안

### 직원 공지용

앞으로 `담당자별 업무`는 실행 기록용, `일일 보고서`는 하루 결과 정리용으로 나눠서 사용합니다.
낮에는 체크와 결과값을 쌓고, 퇴근 전에는 시스템이 모은 근거를 바탕으로 결과/영향/이슈/지원 요청만 정리해 주세요.

### 팀장 공지용

일일 보고서는 업무 체크 현황을 다시 보는 화면이 아니라, 하루 동안 실제로 나온 결과와 리스크를 판단하는 화면입니다.
확인완료 처리 전에는 `결과가 명확한지`, `영향이 보이는지`, `지원이 필요한지`를 기준으로 검토해 주세요.
